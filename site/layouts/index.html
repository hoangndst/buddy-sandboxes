Isolated sandboxes for agents.

Run agents on your cluster. Isolation, a fenced network, and keys that never enter the pod.

Read the quickstart GitHub

Declare a Sandbox. Keep the rest out.

The controller builds the pod, the network, and the deadline from one resource.

Kernel isolation

Run under gVisor or Kata, with a read-only root and hard limits on CPU and memory.

apiVersion: sandboxes.buddy.io/v1alpha1
kind: Sandbox
spec:
  runtimeClassName: gvisor
  maxDurationSeconds: 3600

Network fence

Block cluster traffic and the cloud metadata endpoint. Allow only the hosts you name.

Keys outside

Provider keys stay in the gateway. The pod gets a short-lived token.

A hard deadline

Set how long the run may last. After creation, you can only shorten it.

From your laptop to a pod.

One request. Four stops. Each with one job.

  1. buddy-sbx

    Sends your tree or a clone, then a terminal or one task.

  2. buddy-api

    Checks the call and holds the keys.

  3. Controller

    Builds the pod and the boundary.

  4. Pod

    Runs the agent inside that fence.

Built for agent work.

Work from your tree, keep disk when you need it, and attach the tools the agent needs.

  • Workstation

    Run, exec, logs, list, and sync. Clone a repo or send a local tree.

  • Workspace

    Scratch space or a volume you keep. Suspend the pod and resume with the same disk.

  • Credentials

    Keys stay encrypted. Git tokens never reach the agent. Model calls go through the gateway.

  • Tools

    MCP servers sit beside the agent as sidecars.

Install the operator.

Go 1.25+, Docker 24+, a Kubernetes cluster, kubectl, and kustomize.

  1. Install the CRDs.

    make install

  2. Deploy the controller.

    make deploy IMG=ghcr.io/hoangndst/buddy-sandboxes-controller:latest

  3. Apply a Sandbox.

    kubectl apply -f sandbox.yaml
